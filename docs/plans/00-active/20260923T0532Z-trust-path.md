# Trust Path — Failed Delete, Import, and Reset

**Status:** Implemented (PR)
**Priority:** High (customer-trust)
**Origin:** Principal-engineer review items 2a / 2b / 2c

---

## Summary

Three write paths can leave Capacitarr believing something that is not true:

1. A live *arr delete that fails after `pending_delete` is written.
2. Settings import that commits preferences/rules/integrations, then fails on disk groups.
3. Data reset that deletes some tables and errors before the rest.

A restore that half-applies, or a `pending_delete` for a title still on disk, is how users stop believing the product. This plan fixes those three paths only. It does not change auth, SSRF, preview pagination, or the event-bus/SSE replay model.

---

## 2a. Failed live delete must not leave `pending_delete`

**Failure mode:** `executeDeletion` writes an audit intent (`CreateIntent` → `pending_delete`), then calls `job.Client.DeleteMediaItem`. On *arr failure it publishes `DeletionFailedEvent` and returns. The intent row stays `pending_delete`. The UI/filter can then show a title as pending-delete while the file is still on disk.

The opposite case (delete succeeded, `MarkDeleted` failed) is already correct and tested: keep the intent, increment `auditPostDeleteFailures`. Do not change that.

**Chosen terminal state:** `cancelled` (already in the audit action CHECK). A new `delete_failed` action would be clearer in the log, but it requires a CHECK-constraint rebuild, OpenAPI, and frontend `AuditAction` edits. This PR keeps the schema/API surface unchanged. `FailIntent` is the method name so call sites read as “the *arr call failed,” not “the user cancelled.” The stored action is still `cancelled`. `DeletionFailedEvent` plus the existing `failed` counter already distinguish this from a user cancel.

**Changes:**

- `AuditLogService.FailIntent(id)`: `pending_delete` → `cancelled`. Same RowsAffected=0 error shape as `MarkDeleted`.
- `deletionAuditor` grows `FailIntent`. Update the real service, the deletion-package test helper, and `mockDeletionAuditor`.
- On *arr delete failure, call `FailIntent`. If that write fails, log and increment a cancel-failure counter — do not leave the error silent.
- Expose `auditPostDeleteFailures` (already exists, not currently published) on `GET /health` and `GetWorkerMetrics`. Same for the new cancel-failure count. Do not flip health to unhealthy solely because the counters are non-zero.

**Test:** Integration-style in `deletion_test.go`: real `AuditLogService` + SQLite, *arr delete fails after intent created → **zero** leftover `pending_delete` rows. `TestExecuteDeletion_KeepsIntentWhenMarkDeletedFails` must still pass. Add `TestAuditLogService_FailIntent` next to the existing intent test.

## 2b. Settings import must be one transaction including disk groups

**Failure mode:** `Import` / `CommitImport` claim “all sections in one transaction.” Preferences, integrations, rules, and channels commit, then disk groups run after commit because `DiskGroupService` uses its own `*gorm.DB`. On SQLite (`SetMaxOpenConns(1)`) calling that handle inside the open tx deadlocks. If disk-group import then fails, prefs/rules/integrations have already landed. Merge and sync are both unsafe.

**Chosen fix:** Import disk groups on the **same** `tx` (not compensating rollback). The deadlock is a second-handle problem, not a “disk groups cannot be transactional” problem. Upsert/list/orphan-delete use `tx` directly with the same SQL as `DiskGroupService.ImportUpsert`. Keep the existing `diskGroups != nil` guard so an unwired backup service still fails closed.

Apply the same change to `CommitImport`.

**Test:** Focused cases in `backup_test.go` (do not rewrite the suite). Seed prefs + integration + rule + an existing disk group. Import those sections plus a disk group that fails mid-flight (SQLite trigger on `disk_groups` for a sentinel mount path). Assert the DB matches pre-import state for **both** merge and sync. Existing happy-path import tests must still pass.

## 2c. `DataService.Reset` must be one transaction

**Failure mode:** Sequential deletes/updates (audit, approval queue, library history, engine stats, disk-group transient fields, integration stats, media cache). A mid-way error tears state: audit gone, queues still there.

**Contract to keep:** Lifetime stats and preferences are **not** cleared.

**Chosen fix:** One `db.Transaction`. All table writes go through `tx`. Delete `media_cache` inside the tx (do not call `PreviewService.ClearPersistedCache`, which uses its own handle and would deadlock). After a successful commit, `InvalidatePreviewCache` (in-memory) and publish `DataResetEvent`. On error, publish nothing.

**Test:** Seed audit + approval + lifetime stats + prefs. Install a SQLite `BEFORE DELETE` trigger on `approval_queue` so step 1 (audit) succeeds inside the tx and step 2 fails. Assert audit still present, approval still present, lifetime stats and prefs untouched, no `data_reset` event.
